# الميزة الدولية لإدخال رقم الهاتف — ملاحظات التكامل (محدّثة: التكامل الكامل تم)

## ✅ القرار المتخذ: الخيار 1 — الاستبدال الكامل

تم تنفيذه بالكامل. الملخص:

## ما تغيّر في كل ملف

| الملف | التغيير |
|---|---|
| `lib/phone.ts` | إضافة `formatPhoneForDisplay()` (لعرض E.164 بصيغة محلية مقروءة) و`phoneToWaMeDigits()` (يشيل الـ + لروابط wa.me) |
| `lib/types.ts` | `Seller.phone` أصبح موثّق كـ E.164 كامل؛ `isValidEgyptPhone` بقيت `@deprecated` (صفر مستدعين الآن، اتسابت كمرجع تاريخي بدل حذفها نهائيًا) |
| `lib/hooks/useProperties.ts` | `ProfileRowFull` بيقرأ `phone_e164` بدل `phone`؛ `rowToProperty()` بيملى `seller.phone` من `phone_e164` |
| `app/publish/create-listing.tsx` | الحقل القديم استُبدل بـ `<PhoneInput>`؛ الحفظ بقى في `phone_e164`/`phone_country_code`/`phone_country_name` بدل `phone`؛ تعديل إعلان قديم بيحوّل الرقم المخزّن رجوع لصيغته المحلية عبر `splitE164()` |
| `app/property/[id].tsx` | **إصلاح الباغ:** رابط `wa.me` بقى بيستخدم `phoneToWaMeDigits()` بدل تمرير الرقم خام — `tel:` كان أصلًا هيتصلح تلقائيًا لأن القيمة بقت E.164 كاملة (مع +) |
| `components/requests/MakeOfferModal.tsx` | نفس نمط `create-listing.tsx` — `PhoneInput` بدل الحقل النصي، تحقق دولي بدل `isValidEgyptPhone` |
| `app/chat/[id].tsx` | تحسين إضافي: رقم الواتساب المعروض في فقاعة الرسالة بقى رابط قابل للضغط (كان نص عرض فقط قبل كده، بما إن القيمة دلوقتي مضمونة الصحة) |
| `supabase/migrations/20260829000000_international_phone_columns.sql` | إضافة الأعمدة الجديدة (كان جاهز من قبل) |
| `supabase/migrations/20260830000000_backfill_phone_e164.sql` | **جديد:** ترحيل الأرقام المصرية الموجودة فعليًا لصيغة E.164 |

## 1️⃣ تحويل البيانات الموجودة

`20260830000000_backfill_phone_e164.sql` بيعمل:
- كل رقم مصري محلي صحيح (`01xxxxxxxxx`) → `+20xxxxxxxxxx` تلقائيًا.
- **عمود `phone` القديم مايتلمسش خالص** — يفضل زي ما هو، فمفيش أي بيانات
  بتتفقد تحت أي ظرف، حتى لو الترحيل فشل أو اتلغى.
- أرقام مش بصيغة مصرية صحيحة (بيانات تجريبية/تالفة) → تتسيب من غير تحويل،
  البائع هيتطلب يدخل رقمه تاني بس لما يعدّل أي إعلان من الفورم الجديد.
- حالة التصادم (رقمين مختلفين طلعوا بنفس القيمة بعد التحويل) → مُعالجة
  صراحة: أقدم حساب (`created_at`) بس هو اللي بياخد الرقم، والباقي يتسيب
  فاضي بدل ما الـ `UNIQUE` constraint يفشّل الـ migration كله. عدد الحالات
  دي بيتسجل في NOTICE وقت التشغيل.

## 2️⃣ الاختبار

### ⚠️ حدود مهمة لازم أكون واضح بيها
**معنديش جهاز حقيقي ولا محاكي متاح في بيئة العمل دي** — كل التحقق اللي
عملته هو فحص static (syntax check بـ `tsc`، مراجعة يدوية للمنطق، فحص كل
استدعاء لـ `phone` في المشروع بالكامل). **لسه محتاج اختبار فعلي على جهاز
حقيقي زي ما طلبت بالظبط** قبل الإطلاق — مقدرش أأكد إن ده تم لأني معنديش
الأداة اللي تخليني أعمل كده بنفسي.

### خطة الاختبار اليدوي المطلوبة (checklist جاهزة للتنفيذ)

**نشر إعلان جديد — لكل دولة من الـ 5:**
| الدولة | رقم تجربة نموذجي | المتوقع |
|---|---|---|
| مصر 🇪🇬 | 01012345678 | `phone_e164` = `+201012345678` |
| السعودية 🇸🇦 | 501234567 | `phone_e164` = `+966501234567` |
| الإمارات 🇦🇪 | 501234567 | `phone_e164` = `+971501234567` |
| أمريكا 🇺🇸 | 2025551234 | `phone_e164` = `+12025551234` |
| بريطانيا 🇬🇧 | 7911123456 | `phone_e164` = `+447911123456` |

لكل صف: اختر الدولة من الـ picker → اكتب الرقم → تأكد إن رسالة الخطأ
بتختفي لو الرقم صحيح وتظهر لو ناقص رقم → انشر الإعلان → افتح صفحة تفاصيل
العقار → اضغط زر الواتساب → **تأكد إن واتساب بيفتح فعليًا برسالة معبأة
مسبقًا** (ده بالظبط الباغ اللي كان موجود) → ارجع واضغط زر الاتصال → تأكد
إن تطبيق الاتصال بيفتح بالرقم الصحيح كامل.

**تعديل إعلان قديم (بائع كان عنده رقم مصري من قبل الميزة):**
- افتح إعلان قديم للتعديل → تأكد إن حقل الهاتف بيظهر معبّى تلقائيًا
  بالرقم الصحيح (مش فاضي، مش +20 ظاهر جوه الحقل نفسه).

**تقديم عرض على طلب (MakeOfferModal):**
- كرر نفس اختبار الدول الخمس من شاشة "تقديم عرض" على طلب عقاري.
- افتح المحادثة الناتجة → تأكد إن رقم الواتساب في فقاعة الرسالة بقى قابل
  للضغط وبيفتح واتساب صح.

**بعد تشغيل migration الترحيل على بيانات حقيقية:**
- اختر 3-5 حسابات بائعين حقيقيين كان عندهم رقم مصري قبل الميزة → تأكد إن
  `phone_e164` اتملى صح، وإن زر الواتساب في صفحاتهم شغال.

## 3️⃣ خطة الـ Rollback

موثّقة بالتفصيل جوه `20260830000000_backfill_phone_e164.sql` نفسها
(3 خيارات: تصفير الأعمدة الجديدة بس، استرجاع من نسخة احتياطية كاملة،
أو حذف الأعمدة نهائيًا). **الأهم: خد نسخة احتياطية قبل التشغيل على
الإنتاج** — الأمر موثّق في أول الملف (`supabase db dump` أو نسخة سريعة
من الجدول نفسه `profiles_backup_pre_phone_migration`).

## 4️⃣ تحذير إضافي اكتشفته أثناء التكامل

`lib/hooks/useChatsDB.ts` فيه عمود `whatsapp` منفصل على مستوى الرسالة
الفردية (مش على مستوى البروفايل) — بيتاخد من `MakeOfferModal.tsx` وبيتخزن
لكل رسالة عرض. اتأكدت إن ده اتحدّث كمان (نفس `PhoneInput`/`validateAndFormatPhone`)
وإن العرض في `chat/[id].tsx` بقى تفاعلي. ده مش كان مطلوب صراحة بالمواصفة
الأصلية لكنه استخدام حقيقي تاني لرقم الهاتف كنت هفوّته لو وقفت عند
الملفين المذكورين بس.
